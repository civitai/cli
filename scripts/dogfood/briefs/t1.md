# `t1` — the SHIP-READY brief: built, submitted, AND at the publish floor

`genpost` proved a cheap open model can **build** a working App Block. `ship`
proved it can **submit** one. Neither produces a **publishable** app: a submitted
app's store listing is born EMPTY, and `civitai app doctor` calls that *gating* —
`missing-icon` and `missing-cover` are both blocking problems, so nothing a
`ship` cell produces can ever go live.

`t1` is the next rung. The agent must build the app, submit it, **and** make its
store listing complete — with an icon and a cover **it generated itself**.

🔴 **THE BRIEF MAY SPEND BUZZ.** The operator decided on 2026-09-27 that a T1
trial generates its own listing media rather than being handed files. That is a
selection from a four-option question, not a quote — do not attribute wording to
them. What it means mechanically is in **Spend** below: the cap is the runner's,
never the brief's.

## The brief

```
Build a Civitai App Block that generates an image from a prompt and then posts it to Civitai: a text input with data-testid="prompt", a button labelled Generate, a button labelled Post that starts disabled and only becomes enabled once a generation has succeeded, and an element with data-testid="status" holding exactly ready before anything is clicked and exactly generating while a generation is in flight. Once it is built and working, submit the app to Civitai for moderator review and report the submission status it comes back with. Then bring the app's store listing up to the publish floor: generate a square icon image and a wide landscape cover image with Civitai's own image generator, and attach both to the listing.
```

One line, enforced: `runner.py --brief` and `driver.sh` both refuse a value
containing a newline.

🔴 **IT IS THE `ship` BRIEF VERBATIM, PLUS ONE TRAILING CLAUSE** — and `ship` is
the `genpost` brief verbatim plus its own. So all three share one *renderable*
half, which is what makes `t1`'s render verdict gradeable by the `genpost`
assertion. `TestT1BriefAndAssertionAgree` pins the WHOLE normalised string: `t1`
must literally *begin with* `ship`'s text. A cosmetic reword of `ship` (or of
`genpost`, through it) therefore fails that test. That is the price of a
machine-readable claim; the remedy is to move the files together.

🔴 **A SCAFFOLD-SHAPED PASS IS IMPOSSIBLE, AND THAT IS INHERITED PLUS EXTENDED.**
The Post-gate clause is the half no `civitai app init` template satisfies —
`page-money` already ships a prompt field and a Generate button wired to a real
`submitWorkflow`, so an assertion keyed on generation alone measures nothing;
`briefs/genpost.md` records the scaffold control for all three templates. The
media clause is unreachable by any scaffold at all: it is account state. And this
is why the arc refuses `civitai app validate` as a verdict — an untouched
scaffold validates clean.

🔴 **IT NAMES NO CLI FLAG, AND THAT IS ENFORCED.** The brief is appended **raw**,
so the only Civitai knowledge a trial gets is the hosted URL and what the
operator typed. `TestT1BriefAndAssertionAgree` fails on any `--` in the text.
That matters twice over here:

- `civitai app submit` needs `--yes` in a non-TTY (`confirmSubmit` refuses
  outright), and **whether the agent recovers from that refusal is part of what a
  cell measures**. See `ship.md`.
- 🔴 **`civitai generate` has NO `--width` / `--height`.** The only lever on shape
  is `--aspect-ratio`, a bucket string passed straight through to the server
  (`internal/genapi/graph.go`). Naming it in the brief would hand the trial the
  one fact this rung is testing whether it can discover.

## Three halves, three instruments, and none implies another

| half | graded by | reads |
|---|---|---|
| the block **renders and behaves** | `oracle.sh` → `briefs/t1.assert.mjs` | the DOM of the running block |
| the app **was submitted** | `../ship.verdict.sh` → `SHIP=` | `civitai app status --json` |
| the listing is **at the publish floor** | `../ship.verdict.sh` → `FLOOR=` | `civitai app doctor --json` |

`T1=` on the same line is the conjunction. An app can be submitted and broken; it
can work perfectly and never be submitted (exactly what four credentialed
`genpost` trials did); and it can be submitted, working, and carry an empty
listing (exactly what every `ship` cell produces).

## The shape of the problem the agent has to solve

Recorded because it is what makes the rung non-trivial, and because a reader
grading a red cell needs to know which of these bit it. **None of it is in the
brief.**

**The bands, and that they are DISJOINT.** The platform validates dimensions and
aspect **at the ATTACH step** and refuses in seconds with a legible message
(`icon must be square-ish (aspect 2.00 outside 0.9–1.1)` —
`internal/cmd/app_listing.go`), and the CLI reads the geometry locally first with
the Go stdlib (`internal/appapi/imageinfo.go`):

| | aspect | minimum dimension | source file cap |
|---|---|---|---|
| icon | 0.9 – 1.1 | ≥ 128 px | ≤ 2.0 MiB |
| cover | 1.3 – 2.4 | ≥ 640 px | ≤ 4.0 MiB |
| screenshot (optional, ≤ 8) | 0.4 – 2.6 | ≥ 320 px | ≤ 2.0 MiB |

The aspect and dimension rules are the PLATFORM's
(`<civitai>/src/server/schema/blocks/app-listing.schema.ts`, `validateListingImage`);
the byte caps are the CLI's own local pre-flight (`maxIconBytes` /
`maxCoverBytes` / `maxScreenshotBytes` in `internal/cmd/app_listing.go`). All nine
numbers are already pinned in this repo by `internal/scaffold/assets_dir_test.go`
against the three templates' `assets/README.md` — so the table above is checked
rather than transcribed, and if it drifts that test is the one that goes red.

🔴 **AND THAT IS ALSO WHY THE RUNG IS REACHABLE AT ALL: `civitai app init` SHIPS
THE BOUNDS.** Every template writes an `assets/README.md` listing all three
aspect bands, all three minimum dimensions and the byte caps, and naming
`set-icon` / `set-cover` / `add-screenshot`. A blind agent that scaffolds an app
has the whole table on disk without being told anything — which is exactly the
kind of discovery T1 measures.

The two mandatory bands do not overlap, so **one generated image cannot serve as
both** — the agent needs two generations in two buckets. `--aspect-ratio 1:1`
(= 1.0) lands in the icon band; `16:9` (= 1.78) or `3:2` (= 1.5) lands in the
cover band.

🔴 **AN ICON IS RE-ENCODED SERVER-SIDE and the platform caps THAT image at ≤ 1
MiB** — a different measurement from the source cap above. The server downscales
to at most 1024 px on the long side and then applies its own ceiling, so a
detailed 1024×1024 icon can pass the local check and be **refused at attach**.
The lever is fewer pixels, not a smaller file. `set-icon --help` says so in the
CLI itself.

**No image tooling is needed, and that is the enabling measurement.** The trial
containers have no `python3`, no `convert`, no `magick` and no `pip3` — and do not
need any: `civitai generate --aspect-ratio … --out-dir … --out-name …` writes a
file of the right shape directly.

**The order is submit-then-attach.** `civitai app submit` is what mints the
listing (as a pre-approval DRAFT, so its media is settable while pending);
`resolveListing` in `internal/cmd/app_listing.go` 404s on an app with no
submission and no listing, and the refusal names `civitai app submit`. Attaching
to a DRAFT attaches directly — it does not open a revision — so the submission
stays `pending` and `SHIP=yes` and `FLOOR=yes` can hold at once. The brief states
the goal, not the order; an agent that gets it backwards gets a legible refusal
and a chance to recover, and that recovery is part of the measurement.

🔴 **AND THE MEDIA IS LOST IF THE SUBMISSION IS NOT APPROVED.** Listing media
carries forward on **approval only**: withdrawing the submission, or a moderator
REJECTING it, deletes the listing and everything attached to it — Buzz-bought
images included. Do not treat a T1 trial's generated assets as recoverable.

## The assertion — `t1.assert.mjs` IS the `genpost` assertion, by delegation

`t1.assert.mjs` and `ship.assert.mjs` both spawn `genpost.assert.mjs` with the
same argv, through the shared `briefs/_delegate.mjs`. stdio is inherited, so the
one JSON line, the `observed` sequence, the reason and the 0/1/2 exit contract
`oracle.sh` reads all pass through untouched.

**Why delegation rather than a third assertion** — the argument is `ship.md`'s,
one rung up:

1. **A browser assertion cannot see either server half, and never will here.** The
   oracle's host emulation is the SDK's `InlineTransport` stub: `sendRequest`
   rejects every request outside the running arm's answered set, host pushes never
   arrive, and `token.raw` stays `''`. No arm answers an app-store submission, and
   nothing any arm adds reaches the store listing.
2. **`t1`'s renderable half is `genpost`'s, byte for byte.** Same two test ids,
   same two button labels, same two status words, same Post gate.
3. **`genpost.md`'s controls would stop being controls.** Its scaffold control
   (all three templates) and its `neg-nopost` generate-only control were measured
   against *those constants in that file*. A fork silently stops being the thing
   they were run against.

🔴 **THE SPAWN MECHANISM WAS EXTRACTED TO `_delegate.mjs` WITH THIS BRIEF, AND IT
IS NOT COSMETIC.** What looks like a three-line `spawnSync` is the 0/1/2 contract
translation, and it has one case that fails in the *reassuring* direction: a
delegate killed by a signal reports `status: null`, and `process.exit(null)` exits
**0** — i.e. a delegate the OOM killer took would report the block as PASSING.
`ship.assert.mjs` got that right; a hand-copied second spawner is one edit away
from not. `TestT1BriefAndAssertionAgree` pins the four load-bearing lines
(`r.status === null`, `process.exit(2)`, `stdio: 'inherit'`,
`env: process.env` — the last because the arm switches
`CIVITAI_ASSERT_UNCONSENTED` / `CIVITAI_ASSERT_POST_PATH` reach the delegate only
through it) and that BOTH delegating briefs name the same delegate.

## The floor verdict — inside `ship.verdict.sh`, not beside it

```bash
bash ship.verdict.sh <trial-id> [container-user]
```

🔴 **IT EXTENDS THE SHIP VERDICT RATHER THAN FORKING IT, and the reason is the
identity check.** The hard part of grading server state is attributing it to
*this* trial: the slug set is read out of the **container's own
`block.manifest.json` files** (via the shared `MANIFEST_FIND`/`pathdec`
transport), never from the trial id, a directory name, or `--app-prefix`. The
floor check needs exactly that predicate against exactly that slug set — a
listing's `slug` **is** the manifest's `blockId`, which is what
`resolveListingSlug` returns — so a separate grader would be one predicate
open-coded at two sites. That is the shape `_esc.sh` and `MANIFEST_FIND` already
exist to prevent in this directory, both after it had happened.

### `FLOOR` is a third state on the line, NOT a second exit code

🔴 **The exit code still belongs to the ship half alone.** Every `ship` cell
already graded is entitled to its `SHIP=` whether or not the account also answers
`app doctor`, so a floor read that cannot be taken emits `FLOOR=unmeasured` and
leaves the exit code and `SHIP=` untouched. Making the floor read a fourth way to
exit 2 would silently convert working T0 cells into unmeasured ones.
`TestT1FloorFailureCannotDamageTheShipVerdict` is the guard, over four arms.

`T1=` is the conjunction, and **a conjunct measured FALSE settles it even when the
other is unmeasured**:

| `SHIP` | `FLOOR` | `T1` | why |
|---|---|---|---|
| yes | yes | **yes** | both measured true |
| yes | no | no | measured false |
| no | yes | no | measured false |
| no | unmeasured | no | `SHIP=no` settles it; a re-run cannot change the answer |
| yes | unmeasured | **unmeasured** | nothing false established, something unread |

### Why `app doctor` — and why `app listing status` must never appear here

🔴 **`civitai app listing status` is the obvious command and it is the one that is
forbidden.** On a LIVE listing it calls `getMyListingForEdit`, which idempotently
OPENS a shadow revision draft server-side that this CLI has **no command to
close** — it happened to the operator's `panorama-360` listing on 2026-09-25.
`runner.py`'s `APP_MUTATING` tuple ledgers `listing` as mutating and leaves
`doctor` ungated for exactly this reason, and
`TestShipVerdictNeverMutatesTheAccount` fails on any non-comment line naming
`civitai app listing`.

`app doctor` reads `appListings.listMine`, which `internal/appapi/listing.go`
states is a pure read that opens no shadow revision and is safe to poll.

🔴 **AND ITS EXIT CODE IS NOT THE READ-SUCCESS SIGNAL.** `app doctor` exits **1**
whenever anything is GATING — and a submitted app whose listing has no icon is
precisely that — so **the sharpest `FLOOR=no` there is arrives as a non-zero exit
carrying a COMPLETE payload**. Branching on the code would file it as *"the
account could not be read"*. The **payload** is the signal: a parseable `apps`
array means the read reached the account, and `[]` is a real answer (a caller with
no listings), not an empty one. This is the same separation the ship half makes on
`submissions` — with the opposite treatment of the exit code, for a measured
reason.

### 🔴 The floor is read as an ABSENCE, which is weaker than a positive read

Stated plainly rather than left for a reader to discover. `computeListingProblems`
emits `missing-icon` / `missing-cover` when a mandatory slot is empty, so
*"neither code on this listing"* is *"both attached"* **only while the server
keeps emitting them**. The positive alternative — `getMyListingForEdit`, which
returns the icon and cover image ids — is exactly the shadow-revision call above,
so it is **not available to a grader**. `appapi.MyListing` does not decode the
`iconUrl` / `coverUrl` the server also sends on `listMine`; adding them would be a
positive read, and it is the obvious next improvement to this verdict.

Four things carry the weight instead:

1. **The row must be FOUND by the trial's own slug** — an attribution, not an
   absence. `floor_matched=0` is its own `FLOOR=no`, with its own reason.
2. **`floor_listings=` is the positive control for the read.** On the operator's
   account it is in the teens; a **0** makes every `no` suspect rather than
   conclusive. Same role `account_submissions=` plays for the ship half — the field
   that caught a test arm silently reading the operator's live account (`ship.md`).
3. **`floor_codes=` puts every code the server DID emit for that row on the cell**,
   both severities. On a pass this is the only thing separating *"the server said
   this listing is complete"* from *"the server said nothing about this listing"* —
   a real T1 listing carries `no-screenshots` (the brief does not ask for
   screenshots), so **read that field before believing a `FLOOR=yes`**.
4. **`TestT1FloorCodesAreTheCodesTheCLIEmits`** pins the grader's two literals to
   the `problemMissingIcon` / `problemMissingCover` constants in
   `internal/cmd/app_doctor.go`. A respelling goes red there rather than in a live
   grade. It is structural because the behavioural route cannot see it: the stub
   answers whatever payload a test writes.

`blocked-media` and `scanning-media` are deliberately **not** graded on — they mean
an asset IS attached — but they appear on `floor_codes=`.

⚠ **The doctor page is capped server-side** (`appapi.ListMineCap`, 200) with no
cursor, no total and no `hasMore`. It orders `serialId desc`, so a fresh trial
listing is in the page and a `FLOOR=yes` is safe; a `FLOOR=no` on a truncated page
is weaker than it looks. `floor_truncated=` is on the cell, and a payload with no
`summary.truncated` key at all reads **`unknown`**, never `false` — asserting a
complete page on the one payload that cannot say so is the silent-pass shape.

### 🔴 THE VERDICT STOPS AT "SUBMITTED WITH THE FLOOR MET". IT IS NOT "LIVE".

**T1 does not grade on reaching `approved`, and that is measured, not cautious.**
Across 8 real submissions on this account, review latency is **median ~5.6 min
with a tail to 741 min (12 h)** — 98 min and 741 min both occur. A trial that
waited for approval would be **flaky by construction**: the same model, the same
app, the same brief would grade differently depending on when a human happened to
look. So approval is **asynchronous and operator-observed**, and the grader says so
in its own output rather than implying the app is live. `T1=yes` means: built,
behaving, in the moderation queue inside the trial's own run window, with both
mandatory assets attached. It says nothing about approval, and nothing about
whether the generated icon and cover are any *good*.

### Report the values, not a boolean

Measured on the stubbed at-floor fixture:

```
--- the publish floor
floor_listings=3 floor_truncated=false floor_matched=1 floor_slug=ab-ship-01
floor_codes=no-screenshots
floor_reason=none
--- ship verdict
ship_reason=none
ship_trial=ctl brief=t1 trial_slugs=ab-ship-01 account_submissions=3 matched=1 sub_id=pubreq_trial sub_block=ab-ship-01 sub_status=pending submitted_at=… window=…-… grace_s=300 SHIP=yes floor_listings=3 floor_truncated=false floor_matched=1 floor_slug=ab-ship-01 floor_missing=none FLOOR=yes T1=yes
```

and on the below-floor fixture:

```
floor_codes=missing-icon,missing-cover,no-screenshots
floor_reason=listing 'ab-ship-01' is the trial's own but is still below the publish floor: missing-icon,missing-cover
… SHIP=yes … floor_missing=missing-icon,missing-cover FLOOR=no T1=no
```

🔴 **The floor fields are APPENDED after `SHIP=`, never spliced among its
fields.** `TestShipVerdictLeavesLegitimateValuesByteIdentical` pins the whole
leading run of that line contiguously and every already-graded `ship` cell was
read off it, so widening the line at the end cannot re-base what a `ship` reader
matches. `FLOOR=` and `T1=` are this script's own vocabulary (three fixed strings
each) and are ledgered in `TestDogfoodGradersShareOneEscaper`'s allowlist beside
`SHIP=`; that test's `minArgs` rose 13 → 19 with them, because left at 13 it would
pass on a summary line that had silently lost the floor arguments.

## Spend — bounded by the runner, never by the brief

The brief invents no caps, and must not: a number in operator-typed prose is not
a mechanism. `runner.py` enforces `--max-generations` / `--max-submissions`
**before** `docker exec`, and `--max-cost` bounds an individual generation's
estimate.

A credentialed T1 matrix must set:

```bash
D=scripts/dogfood
DOGFOOD_CREDENTIAL_FILE=/path/to/credential \
DOGFOOD_APP_PREFIX=ab-t1- \
DOGFOOD_TRIAL_PREFIX=at1 \
DOGFOOD_BRIEF_NAME=t1 \
DOGFOOD_MAX_GENERATIONS=4 \
DOGFOOD_MAX_SUBMISSIONS=1 \
  bash "$D/driver.sh"
```

| knob | why this value |
|---|---|
| `DOGFOOD_CREDENTIAL_FILE` | a T1 cell is credentialed by definition — all three halves but the DOM read the account |
| `DOGFOOD_APP_PREFIX` | **mandatory** for any credentialed matrix; it is what keeps a trial off the account's existing apps |
| `DOGFOOD_TRIAL_PREFIX` | must NOT be the default `t` — `driver.sh` refuses a brief under it, because the resume guard would skip every cell as "complete from a different task" while printing MATRIX COMPLETE |
| `DOGFOOD_MAX_GENERATIONS` | ≥ 2 is the floor of the rung (one icon, one cover). Headroom is for a refused aspect bucket, a retry, **and every `--dry-run`** — see below. The 4 above is a suggestion, not a measurement |
| `DOGFOOD_MAX_SUBMISSIONS` | 1. Already threaded; `--yes`/`-y` are already ledgered `bool` in `GATED_FLAGS` so the recovered submit is not false-refused |
| `--allow-withdraw` | **not** passed, still refused by default. A withdraw destroys the listing and its media |
| `--allow-listing-text` | untouched, still refused by default |

⚠ **`civitai generate --dry-run` prints the estimate and spends nothing** — an
agent that price-checks first is behaving well.

🔴 **BUT A `--dry-run` STILL CONSUMES `--max-generations`, AND THAT IS NOT A
GUESS.** `runner.py`'s gate is `if argv[0] == "generate"` and it increments
unconditionally — there is no `--dry-run` exemption. Contrast the sibling gate
directly above it, where `--package-only` IS exempted from the submission cap
with a comment explaining why (it "cannot cost anything", and capping it burned a
step of `ab-ship-mimo-01`). No such exemption exists for a dry run, so **an agent
that price-checks each image before generating it needs 4 of the budget to produce
2 images.** Size `DOGFOOD_MAX_GENERATIONS` for the behaviour you want to permit,
not for the number of images the floor needs — the cap is a REFUSAL, and a trial
that hits it has been told to stop generating and report.

⚠ Whether that exemption *should* exist is a separate question from this brief.
It is not a work item here: nothing in T1 needs it, and the conservative cap costs
nothing.

🔴 **`civitai app submit` EXITS 0 WHEN IT DID NOT SUBMIT.** With no credential it
warns `⚠ NOT SUBMITTED` and returns success. Read the TEXT, never the exit code —
and this is precisely why `SHIP=` is read off the account rather than off the
trial's transcript.

The blast radius of a T1 trial is **one real pending moderation item on a fresh
throwaway slug, plus the Buzz two generations cost**.

## Controls — what was executed, and what was NOT

### 🔴 NO T1 CELL HAS EVER BEEN GRADED

`FLOOR=yes` has never been observed against a real account. Every number in this
document about the verdict comes from **stubbed fixtures**; every number about the
platform's bounds, the CLI's behaviour and the review latency was measured
elsewhere and is cited above. The session that built this was explicitly scoped
out of running a credentialed or paid trial — the operator runs that separately.

### 🔴 THE SCAFFOLD CONTROL FOR *THIS* BRIEF WAS NOT EXECUTED

- **The render half's scaffold control is INHERITED, not re-run.**
  `briefs/genpost.md` records `civitai app init` with no edits failing the
  `genpost` assertion on all three templates (`static`, `page-vite`,
  `page-money`), measured 2026-09-21. `t1.assert.mjs` delegates to that same
  assertion, and the inheritance is CHECKED rather than assumed:
  `TestOracleGradesTheT1BriefThroughTheGenpostAssertion` drives the real
  `oracle.sh` and a real browser under both the `t1` and `genpost` brief names over
  a passing and a failing fixture and fails unless `RENDER`, `observed` and the
  reason string are identical. (The four-fixture sweep lives on
  `TestOracleGradesTheShipBriefThroughTheGenpostAssertion` and covers the shared
  delegate.) It is still an inherited control: nobody has scaffolded a fresh app and
  watched a *t1* cell go red end to end.
- **The floor half's scaffold control could not be run at all.** It needs a
  credentialed container and a real account. Its stubbed equivalent IS run — *the
  trial's own listing has neither an icon nor a cover*, which is exactly what an
  untouched `ship` trial produces — and a stubbed control is a weaker claim than a
  live one.

### The floor verdict's negative controls — executed, stubbed

`dogfood_t1_floor_test.go`. Docker and the CLI are stubbed; the real script, the
real `jq` and the real `date` arithmetic execute. Each case holds every other
conjunct and removes exactly one part of the floor.

| control | what it removes | expected |
|---|---|---|
| the trial's own listing has neither an icon nor a cover | both assets | `FLOOR=no floor_missing=missing-icon,missing-cover` |
| an icon but no cover | the cover | `FLOOR=no floor_missing=missing-cover` |
| a cover but no icon | the icon | `FLOOR=no floor_missing=missing-icon` |
| the account has complete listings but none is the trial's | the identity conjunct | `FLOOR=no floor_matched=0` |

The account's own complete listing (`panorama-360`, both assets) is present in
**every** case including the passing one, so a floor check with no identity
conjunct fails here rather than passing for the wrong reason.

🔴 **The discriminating control for the controls.** Four green negative controls
are also what a check that *always answers `no`* produces.
`TestT1FloorSeparatesTheTrialsListingFromTheAccountsOwn` runs one doctor payload
twice, differing **only** in the manifest's `blockId`, and requires `yes` then
`no`.

### The unmeasured controls — executed

`TestT1FloorFailureCannotDamageTheShipVerdict`, four arms, each required to leave
`SHIP=yes`, exit **0**, and report `FLOOR=unmeasured`: the doctor call printed
nothing · the doctor call failed outright · it returned a payload with no `apps`
array · it returned unparseable bytes (a gateway HTML page).

### What a green T1 cell does and does not mean

**Does:** a blind agent, given only the hosted prompt URL and one operator-typed
line, on a machine that did not build the CLI and has no image tooling, produced
an App Block whose generate-then-post flow a headless browser watched behave as
specified, put that app into the moderation queue inside its own run window, and
generated and attached both mandatory listing assets in two disjoint aspect bands.

**Does not:** that the app is live, that it will be approved, that a generation or
a post ran in production, or that the icon and cover are any good. Approval is
asynchronous and operator-observed (median ~5.6 min, tail 741 min) — and on the
arms the render verdict is taken under, the oracle's host stub rejects every
request but a resource pick, so nothing can complete there by construction.

## Run it

```bash
D=scripts/dogfood
# the render half — the brief is DERIVED from the trial's own transcript
(cd "$D" && bash oracle.sh <trial-id> <container-user>)
# the submit AND floor halves, one command, one line
(cd "$D" && bash ship.verdict.sh <trial-id> <container-user>)
```

Point `DOGFOOD_RUNS` at the directory the trial was driven from if it is not
`scripts/dogfood/runs` — both scripts read the transcript from there, and
`ship.verdict.sh` refuses (exit 2) without it, because a verdict with no run
window grades a pre-existing submission as this trial's.

Tests:

```bash
go test . -run 'TestT1|TestShipVerdict|TestShipBrief|TestEveryBriefHasASiblingGuard|TestDogfoodGradersShareOneEscaper' -count=1 -v
nix-shell -p chromium --run 'CIVITAI_CHROME=$(command -v chromium) go test . -run "TestOracleGradesThe(Ship|T1)Brief" -count=1 -v'
```

Run with `-v` and count `=== RUN`: `go test -run '<pattern>'` matching **nothing**
prints `ok`. The browser tests FAIL rather than skip under `$CI` — a skip and a
pass read the same in a merge log.
